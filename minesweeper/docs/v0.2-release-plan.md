# Future Minesweeper web integration plan

Status: future work, September 22, 2026. This plan was originally drafted as
a Minesweeper 0.2 update inside the playground. The standalone
[Minesweeper Thinking Lab](https://github.com/imom39a/minesweeper-thinking-lab)
v0.1.0 release publishes the three experiments and research first. The shared
controller and Solver Lab specified here have not shipped.

## Release decision

For the next web update, integrate the stronger deterministic Minesweeper
solver with an optional System One / System Two research mode. Make code-only
solving the default in that new interface. Label the Jev → LLM cascade experimental.

The standalone research preview includes the existing browsers, runnable CLI,
article, architecture guide, and recorded results. A later product release
depends on the web integration and verification below. Keep those stages
explicit in documentation.

The evidence supports that positioning: the stronger solver completed 52/100
held-out expert boards versus 32/100 for the old heuristic. The small live
hybrid pilot did not demonstrate additional reliability. See the
[research report](system-one-system-two-research.md) and
[published article](system-one-system-two-article.md).

The dedicated repository is [imom39a/minesweeper-thinking-lab](https://github.com/imom39a/minesweeper-thinking-lab).
It has its own version sequence starting with the `v0.1.0` research preview;
`v0.2.0` is a possible future integration release, not a claim of present functionality.

## 1. Build one shared session controller

Add `minesweeper/session.py` to own a game session, its configuration, public
observation revision, transition policy, budgets and events. Extract reusable
episode logic from `benchmark.run_game()` instead of maintaining independent
web and benchmark implementations. Keep hidden layout access in the game
transition/evaluator, outside the decision interface.

For each turn:

1. Snapshot the public board and run `solver.analyze()` once. Use component
   cap 48 and 200,000 search nodes as the initial release configuration;
   preserve explicit incomplete-search status and bounded global weighting.
2. Apply proven-safe reveals in interruptible batches, checking deadlines and
   stop/pause state between reveals. Refresh observations afterward.
3. If no proof is available, construct the minimum-computed-risk candidate
   set. A unique allowed guess goes directly through code: neither model can
   change that action under the current guard. Label it a guess, not a proof.
4. For remaining ties, use the chosen strategy: code, Jev, LLM or hybrid.
   Hybrid batches the Choice and independent review Noul in one request.
5. Before committing a provider result, recheck session ID, board revision,
   stop/pause state, deadline and candidate membership. Reapply the same risk
   rule in every strategy.
6. Emit a decision event and reveal the accepted cell. Provider failures or
   exhausted budgets produce explicit unfinished states. Any deterministic
   correction of an invalid recommendation is labeled in the event.

Questions, review threshold, tolerance and provider limits remain together in
`hybrid.py` or one shared policy configuration. Keep the existing 0.65 review
threshold marked experimental until evaluated on development cases and then
frozen for new held-out runs. Do not treat Choice confidence as mine safety.

Done when CLI and server produce the same code-only decisions and terminal
outcomes for the same seed/configuration, proven-safe and unique-choice turns
use zero provider requests, and stale responses cannot mutate a game.

## 2. Add a Solver Lab to the web app

Add `/lab/` using the existing dependency-free Python/HTML/canvas stack. Offer
code-only solving as the initial experience and a comparison preset with two
independently selectable strategies. Choices: **Code**, **Jev**, **LLM** and
**Hybrid · experimental**. Provider-backed modes are available according to
the configured credentials; code-only mode works without keys.

Use the same seed, opening and solver configuration for compared lanes. Give
each lane its own elapsed time and outcome; a losing lane must not freeze the
other lane's timer. Clearly distinguish full wins, losses, abstentions,
timeouts and provider failures. Keep old routes available as legacy demos and
link them to the Solver Lab so users can identify which policy they are seeing.

Show the information that helps someone understand the run:

- Proven-safe reveals and guesses as separate counts.
- Selected cell's mine risk, labeled **exact** or **estimated**.
- Decision source: code, Jev or LLM review, with a short escalation reason.
- Provider calls, provider time, local computation time and known cost.
- A decision timeline, pause/stop controls and JSON result export.
- A research link explaining the architecture, measured results and limits.

Keep model preference confidence separate from mine risk. Do not label the
first lane to stop as the winner. Stream bounded event batches rather than
one full-board update per proven-safe cell.

Done when a user can run code-only without credentials, compare two strategies,
understand why a guess happened, stop during an in-flight request, and export
the configuration and outcome through the browser.

## 3. Verify the integrated release

Preserve the existing solver correctness tests and add behavior tests for the
shared session: zero-call proof/unique-choice paths, pause/stop/restart during
inference, stale revisions, deadlines after flood reveals, provider failure,
and model attempts to exceed the risk rule. Update server tests that currently
expect random fallback or a shared first-finish clock.

Run browser checks covering a no-key code game, a paired seeded game,
pause/resume/stop, a provider failure, and export. Use mocks for deterministic
failure tests and a small capped live run to verify actual provider wiring.

Reproduce the recorded code-only benchmark under the same configuration:
52/100 wins on 30×16/99 seeds 100–199, cap 48. After integration, these seeds
are regression fixtures, not a new independent test. Freeze release behavior
and evaluate fresh seeds, such as 200–299, for a new generalization estimate.
Include 50×50, 100×100 and bounded 500×500 checks with full outcomes reported.

Do not block this release on proving a hybrid advantage. Its release criterion
is correct, bounded, transparent operation as an experiment. Promotion to the
default requires a later controlled study: code/Jev/LLM/hybrid on the same
solver, genuine multi-candidate tie states, full paired episodes, and random
escalation at a matched LLM-call rate. Report unsuccessful decisions, S2 rescues
and harms versus the guarded S1 action, and total latency/cost. Select the
acceptable tradeoff before inspecting the new held-out outcomes.

## 4. Package the future web release

The v0.1.0 standalone release publishes the current experiment. The next release
should describe its concrete web behavior after integration and verification:

1. Update the [article](system-one-system-two-article.md) and research with new
   results, preserving the original raw pilots and their limitations.
2. Update the run guide, root README, package/server version, and changelog.
3. Review the shared controller and interface together, with commands verified
   from a clean checkout and browser checks covering the complete user flow.
4. Publish a versioned GitHub release linking the article, architecture,
   reproducible code, and result artifacts.

A hosted provider-backed demo is a separate deployment. The research preview
is available as repository documentation, source code, and data; it does not
promise a publicly hosted live model service.

Suggested future release title: **Minesweeper Thinking Lab 0.2 — stronger solving
in the browser**.

The current headline finding remains: **Stronger constraint solving improved
held-out expert completion from 32% to 52%; our initial Jev + LLM pilot did not
add a demonstrated reliability benefit.** The architecture is useful to share
as an implemented CLI experiment. The release must not imply hybrid superiority,
guaranteed large-board completion, or validated physical-drone safety.

## Follow-up after the release

Prioritize incremental frontier updates and deterministic lookahead among tied
guesses, then measure whether learned routing adds anything beyond those
baselines. Transfer the session revision checks, proposal/execution separation
and failure telemetry into drone simulation before considering physical flight.
The drone experiment needs its own perception, latency, intervention and
collision measurements; Minesweeper thresholds and completion rates do not
transfer directly.
